# LL-235 — PostgreSQL Supabase y esquema Django

Estado técnico: implementada y verificada en el proyecto Supabase de pruebas existente. Fecha local: 2026-11-16; comprobación final UTC: 2026-11-17 04:45. Subtareas de conexión/TLS/pooling y modelos/constraints/migraciones cubiertas. Jira no actualizado: no hay conector disponible en esta sesión. LL-244 se evalúa por separado; esta evidencia no cierra sus criterios de staging/alertas/CI remoto.

## Entrega

Django/DRF gestiona escrituras y esquema de negocio; PostgreSQL permanece alojado en Supabase. Auth y Storage siguen en Supabase. Ocho migraciones adoptan 15 tablas, constraints/índices/defaults/cascadas, identidad UUID estable y funciones privadas de cierre de cuenta. La adopción preservó por SHA-256 los valores originales de las 14 tablas preexistentes. Se añadió customer_identities y la columna rewards.audience_segment. No se asignaron puntos o permisos ficticios.

Docker usa `loyloop_backend`, separado del propietario de migraciones, sin superusuario/DDL/BYPASSRLS ni acceso general a Auth. Secretos y CA fuera de Git/imagen. TLS verify-full hacia el pooler y HTTPS local con CA verificada. El inicio no migra automáticamente.

Admin y móvil pasan identidad, membresías, ofertas, equipo, solicitudes, perfil y reclamos por Django. Se eliminaron escrituras/RPC de negocio y fallback directo. El BFF web usa cookie HttpOnly y comprueba origen; la API autoriza UUID Auth y tenant desde servidor. La navegación y diseño existentes permanecen. Lecturas de catálogo y operaciones propias de Supabase Auth/Storage conservan su servicio.

## Comprobaciones y límites

- Backend: 24 pruebas unitarias correctas; suites PostgreSQL/API reales correctas. El transporte Auth de esas suites está simulado. La comprobación final contra Auth real es independiente.
- `python backend/scripts/docker.py database-check`: TLS y consulta solo lectura correctos con rol runtime. `pool-check`: 60/60 consultas y conexiones devueltas.
- `python backend/scripts/verify_live.py --use-configured-demo`: health/readiness públicos sin credenciales; sesión y CRUD solo en https://localhost:8443 con CA confiable; denegación REST y permisos SQL verificados. Evidencia privada saneada: backend/.docker/ll235-live-evidence.json.
- Backup/restore privado: backend/.docker/backups/20261117T042057Z-cf3b11/. No subir dump, sesiones, contraseñas o datos personales. Este restore no incluye archivos binarios Storage ni toda la configuración Supabase.
- El bundle iOS no demuestra cámara/SecureStore en dispositivo. No hubo cambios visuales/nativos en esta HU; falta el recorrido manual de clientes publicados/dispositivo tras su propio despliegue. No se declara desplegado el admin publicado.
- El túnel temporal necesita PC/Docker encendidos y puede cambiar al reiniciar. Comprobar nueva URL y actualizar configuraciones privadas; no guardarla como dirección estable.
