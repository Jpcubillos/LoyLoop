# LL-232 — Preparar proyecto Django y configuración segura

Fuente: Jira LL-232 y épica LL-231, subtareas LL-233 y LL-234. Consultadas el 2026-11-08.

## Alcance y decisiones

- Bootstrap independiente en `backend/` dentro del workspace, sin cambiar las rutas, reglas o datos de las HUs LL-11..LL-38. El repositorio Django puede extraerse más adelante si se decide separarlo.
- Django 5.2 LTS, DRF y CORS con versiones y dependencias fijadas en `backend/requirements.txt`; settings `local` y `production`.
- Clave requerida en todas las configuraciones; en producción, hosts explícitos, debug desactivado, CORS restrictivo, HTTPS, HSTS y cookies seguras. La confianza en cabeceras de proxy es explícita y desactivada por defecto. HSTS de subdominios y preload son opciones separadas para no afectar dominios no verificados.
- DRF parte con `IsAuthenticated` por defecto y sin implementación de JWT hasta la HU correspondiente. Solo `/health/` es público y no depende de datos. SQLite es local; el motor de producción es dummy hasta LL-235. Esto no demuestra preparación para atender operaciones de negocio.
- El archivo `backend/.env.example` documenta nombres y valores de ejemplo sin credenciales; no se carga automáticamente.
- `.github/workflows/django-backend.yml` prepara CI con Python 3.11/3.12, instala los requisitos y ejecuta los mismos tres comandos de verificación.

## Criterios y evidencia local

| Criterio | Evidencia |
| --- | --- |
| Arranque y healthcheck local | `python scripts/smoke_http.py` inicia un proceso Django real con una clave efímera y consulta `GET /health/`: HTTP 200, `{"status":"ok"}`. El proceso se cierra al acabar. |
| Healthcheck y comprobaciones en CI | Workflow versionado con dependencias fijadas, suite, smoke HTTP y `check --deploy`. Los comandos se verifican localmente; la ejecución real en GitHub Actions está pendiente de que se suba el workflow. |
| Secretos ausentes fallan seguro | `python -m unittest discover -s tests -v`: comprueba clave ausente/corta y que el error no revela su valor. Las claves de test son efímeras. |
| Configuración sin credenciales | `.env.example` sin valores secretos; `.venv`, `.env` y SQLite locales ignorados por Git. Las configuraciones no contienen claves predeterminadas. |
| CORS, hosts y TLS | Suite comprueba origen permitido/denegado, host inválido, rechazo de comodines y orígenes HTTP en producción, HTTPS obligatorio, cookies seguras, HSTS, configuración de proxy y rechazo de cabecera falsificada. |

Resultados del 2026-11-08 en Windows:

- Python **3.11.9** y **3.12.10**: `python -m unittest discover -s tests -v`, **9/9 pruebas correctas** en cada versión.
- En ambas versiones: `python scripts/smoke_http.py` inició Django y comprobó `/health/` por HTTP; `python scripts/check_deploy.py` terminó sin problemas ni advertencias silenciadas usando un dominio y una clave ficticios de CI.
- En Python 3.11: `python -m pip check` sin dependencias rotas. `python manage.py migrate --noinput` aplicó únicamente las migraciones incorporadas de `auth`, `contenttypes` y `sessions` al SQLite local ignorado por Git.
- Se comprobó que `.venv`, el SQLite local y el entorno auxiliar de pruebas quedan ignorados. La comprobación de Django `--deploy` en CI usa HSTS con subdominios y preload para un dominio ficticio; la decisión sobre un dominio real queda pendiente.
