# LL-22 — Escaneo y validación de transacción

Fecha de implementación: 2026-11-20.
Rama: `feature/client-qr-merchant-validation`
Estado: Implementada con pruebas automatizadas y contratos frontend/backend integrados.

## Objetivo y alcance

Permitir a los operadores autorizados del comercio (`owner`, `manager`, `cashier`) escanear o ingresar el código de un cliente, previsualizar de forma segura el detalle de la operación (cliente, tipo de beneficio, condición y vigencia) y confirmar explícitamente la operación de forma atómica e idempotente.

Complementa y cierra el ciclo de la historia cliente de presentación de QR y código manual accesible de 16 dígitos.

## Subtareas cubiertas

1. **Flujo de validación y registro:**
   - **Lado Cliente:**
     - Generación de token temporal de un solo uso en QR y código numérico manual accesible de 16 dígitos (`mobile/src/components/QRClaimCard.tsx` y `components/claim-qr.tsx`).
     - Soporte para accesibilidad (`accessibilityLabel`, `accessibilityRole="text"`, formato legible agrupado de 4 en 4 dígitos).
     - Emisión con `Idempotency-Key` en cliente para tolerar reintentos seguros ante fallos de red sin duplicación (`mobile/src/lib/claims.ts`, `mobile/src/lib/business-api-client.ts`).
     - Expiración de 5 minutos en servidor; reclamos expirados o rechazados requieren generar un nuevo código y nunca consumen cupo ni puntos.
   - **Lado Backend (Django + DRF):**
     - Nuevo endpoint de previsualización `POST /api/v1/businesses/<uuid:business_id>/claims/preview/` y `/api/businesses/<uuid:business_id>/claims/preview/`.
     - `preview_claim(*, business, code)` en `backend/loyalty/domain_services.py`:
       - Verifica pertenencia estricta al comercio autenticado (tenant) y roles autorizados (`owner`, `manager`, `cashier`).
       - Resuelve el código por hex de QR o hash SHA-256 de código manual de 16 dígitos.
       - Valida que el código esté `pending` y no haya expirado (`expires_at <= timezone.now()`).
       - Retorna el nombre del cliente, tipo de beneficio y detalle descriptivo **sin modificar la base de datos ni consumir cupos**.
     - Confirmación explícita `confirm_claim(*, business, code, actor_id)`:
       - Transacción atómica (`transaction.atomic` + `select_for_update`) que consume el reclamo una sola vez.
       - Revalida elegibilidad, cupos y vigencia en el instante de la confirmación bajo bloqueo de fila.
       - Los puntos acumulados locales son permanentes y **nunca se debitan** (`points_balance` no se reduce en redenciones).
       - Registra `LoyaltyEvent`, `StampCompletion` o `RewardRedemption` y marca `claim.status = 'approved'`.
       - Auditoría de evento con actor y tenant (`audit_success`).
   - **Lado Panel Web (`app/dashboard/validar`):**
     - Flujo en dos pasos en `components/claim-validator.tsx`:
       1. Escaneo por cámara o ingreso manual de código -> Consulta `/api/claim-requests/preview`.
       2. Muestra tarjeta de confirmación con datos verificados del cliente y beneficio, con botones explícitos:
          - "Confirmar canje" (Aplica la transacción atómica).
          - "Cancelar" (Descarta la previsualización sin alterar cupos ni reclamos).
       3. Notificación de éxito con resumen y botón para escanear el siguiente cliente.
       4. Manejo de errores recuperable (códigos expirados, ya procesados o de otro comercio) sin bloquear el escáner.

2. **Pruebas de aceptación e integración:**
   - Pruebas de frontera web (`tests/backend-boundary.test.cjs`):
     - Verificación de sesión requerida para previsualización y validación.
     - Bloqueo de peticiones cross-origin a `/api/claim-requests/preview`.
     - Autorización estricta por tenant asignado en servidor.
   - Pruebas de integración DRF (`backend/scripts/test_domain_api.py`):
     - Previsualización exitosa con datos de cliente y beneficio sin mutar saldos ni tarjetas de sellos.
     - Denegación de previsualización para clientes o roles no autorizados (403).
     - Confirmación explícita atómica con sello/redención aplicada una sola vez.
     - Reintento con código ya procesado rechazado con 409 (idempotencia).
     - Códigos expirados o de otro comercio rechazados.
     - Los puntos históricos se preservan y no se descuentan.

## Criterios de Aceptación verificados

| Criterio | Verificación técnica |
|---|---|
| Solo operador autorizado | Verificado en servidor con `business_for(request.user, business_id, {'owner','manager','cashier'})`. Clientes o terceros reciben 403. |
| Comercio y cliente validados | Código resuelto bajo filtro `business=business` y verificación de `BusinessMembership`. Códigos de otro comercio reciben 404. |
| Confirmación explícita | Separación entre `preview_claim` (inspección) y `confirm_claim` (aplicación). Cancelación o abandono no consume cupo. |
| Transacción idempotente | `select_for_update`, bloqueo atómico y rechazo 409 en reintentos ya procesados. Emisión con `Idempotency-Key` en cliente. |
| Sin débito de puntos | `points_required` opera como umbral de elegibilidad; el balance de puntos nunca disminuye. |
| Error recuperable | Manejo de 400, 404 y 409 con mensajes amigables y botón de reintento/limpieza sin recargar la aplicación. |
