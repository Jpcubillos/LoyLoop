## Incidencias corregidas durante la verificación

El primer receptor dependía de Django y no podía recibir una alerta mientras la API estaba detenida. Se sustituyó por un proceso independiente, autenticado y sin puerto público. También se corrigió la recarga de configuración montada de Prometheus/Alertmanager; no se relajaron umbrales ni se simularon notificaciones para hacer pasar la prueba.

El DNS de Python en Windows falló al preparar una sesión nueva. Se verificó una resolución puntual con el resolver del sistema y se añadió una opción operativa temporal que conserva hostname/SNI/CA; no se cambió el DNS global ni se desactivó TLS.

## Alcance y operación

Staging es un entorno Docker separado en este PC, con DB sin red y acceso por socket privado. Auth verifica con el proyecto Supabase de pruebas; los cambios de negocio del smoke se limitan a la copia restaurada. El recorrido autenticado usa únicamente HTTPS local; el rechazo previo de enviar tokens por Cloudflare se respeta. No es despliegue permanente, alta disponibilidad ni prueba nativa de la app.

Las notificaciones van a Alertmanager y al receptor/log local; no se enviaron mensajes a terceros ni se configuró email/Slack. Los backups no incluyen binarios Storage/configuración completa del proyecto y no hay RPO/RTO de producción comprometido. Reproducción, arranque tras apagar el PC y límites en [OPERATIONS.md](../../../backend/OPERATIONS.md). La evidencia de conexión/corte de base corresponde a [LL-235](LL-235.md).

## Resolución de la revisión — 2026-11-17

Los tres hallazgos quedaron comprobados tras los ajustes. Los contratos API completos pasaron bajo SET ROLE loyloop_backend (incluidos administración, identidad y cierre de cuenta; transporte Auth simulado). Staging pasó el recorrido HTTPS con login real loyloop_backend, credencial independiente y sin montar la credencial propietaria en la API. Los fixtures y migraciones se ejecutan en el servicio maintenance separado.

Dos ciclos consecutivos de despliegue/rollback pasaron conservando el mismo recovery_socket. Después pasaron dos ensayos independientes: fallo de migración transaccional (tabla de prueba ausente tras rollback) y fallo de arranque con exit 42. Ambos recuperaron imagen/socket previos y pasaron el smoke autenticado con rol mínimo. Cada ejecución conserva su propio estado; un fallo inesperado no se clasifica como fallo controlado exitoso.

El apagado dejó un ensayo interrumpido, registrado como interrupted_pc_shutdown y repetido en ejecuciones nuevas. Se corrigió además la retención de imágenes de rollback: se resuelve el manifiesto de Config.Image y se conserva una etiqueta privada por ejecución antes de reconstruir una etiqueta existente. No se cambiaron los datos de negocio remotos de Supabase.
