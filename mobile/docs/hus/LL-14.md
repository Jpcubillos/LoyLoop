# LL-14 — Alta y configuración básica de comercio

Fecha de implementación: 2026-11-20.
Rama: `feature/client-qr-merchant-validation`
Estado: Implementada con pruebas automatizadas y contratos frontend/backend integrados.

## Objetivo y alcance

Permitir a los operadores autorizados del comercio (`owner`) configurar la información de su negocio (nombre, categoría, sedes/dirección, ciudad, descripción del programa de fidelización y estado operativo) para publicar y gestionar su programa de lealtad.

## Subtareas cubiertas

1. **Modelo y API de comercios:**
   - **Backend Django + DRF:**
     - Endpoint `GET /api/v1/businesses/<uuid:business_id>/` y `PATCH /api/v1/businesses/<uuid:business_id>/` en `BusinessCatalogView` (`backend/loyalty/v1_api.py` y `backend/loyalty/urls.py`).
     - Autorización estricta por rol/tenant en servidor: solo el `owner` puede modificar los datos del comercio (`business_for(request.user, business_id, {'owner'})`). Clientes, cajeros o terceros reciben `403 PermissionDenied`.
     - Validación de datos mediante `BusinessUpdateSerializer`:
       - `name`: 1..160 caracteres, no vacío ni espacios en blanco.
       - `category`: 1..120 caracteres, no vacía.
       - `address`: dirección física / sedes principales (hasta 300 caracteres).
       - `city`: ciudad principal (hasta 120 caracteres).
       - `description`: descripción del programa de lealtad (hasta 3000 caracteres).
     - Transacción atómica (`transaction.atomic` con `select_for_update`) que persiste en PostgreSQL.
     - Registro de auditoría del evento administrativo con `audit_success(actor_id, business.id)`.
     - Exposición del estado operativo y de suscripción/plan (`status`).

2. **Interfaz de configuración y pruebas:**
   - **Panel Web Next.js (`app/dashboard/configuracion`):**
     - Sustituido el formulario estático por un formulario funcional conectado mediante la Server Action `updateBusinessProfile` (`lib/actions/app-users.ts`).
     - Carga los datos reales del comercio (`getCafeCentral()`) mostrando nombre, categoría, dirección/sedes, ciudad y descripción.
     - Muestra el badge de estado del comercio ("Estado: Activo").
     - Validación en cliente y servidor con redirección y revalidación de ruta (`revalidatePath`).
     - Protegido por roles: solo usuarios con rol `owner` pueden ingresar a `/dashboard/configuracion` (`lib/auth-access.ts`).

3. **Pruebas de aceptación e integración:**
   - **Pruebas de frontera web (`tests/backend-boundary.test.cjs`):**
     - Verificación de que `updateBusinessProfile` envía la petición PATCH al tenant autorizado en servidor.
     - Rechazo de datos con nombre vacío.
     - Verificación de restricción de acceso: cajeros y gerentes no tienen permiso de configuración, solo el dueño (`owner`).
   - **Pruebas de integración DRF (`backend/scripts/test_domain_api.py`):**
     - Consulta de datos de comercio (`GET /businesses/{id}/`).
     - Modificación exitosa de nombre, categoría, dirección (sedes), ciudad y descripción por el dueño.
     - Rechazo de modificación para clientes (403), cajeros (403) y comercios ajenos (403).
     - Validación de nombre en blanco rechazada con 400.
     - Persistencia confirmada en base de datos.

## Criterios de Aceptación verificados

| Criterio | Verificación técnica |
|---|---|
| Nombre, sedes y estado | Campos `name`, `address` (sedes), `city`, `category`, `description` y `status` persistidos y expuestos en API y formulario web. |
| Configuración editable | Endpoint `PATCH /businesses/{id}/` y formulario web con Server Action `updateBusinessProfile` permiten actualización reactiva. |
| Datos validados | Serializer valida longitudes, campos no vacíos y tipos antes de escribir en la base de datos (400 si son inválidos). |
| Solo usuarios autorizados editan | Restringido exclusivamente al rol `owner` del tenant autenticado en servidor. Otros roles o terceros reciben 403. |
