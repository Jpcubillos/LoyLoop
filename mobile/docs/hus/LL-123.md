# LL-123: [MVP] Beneficios con filtros Todos, Recompensas y Promociones

## Descripción de la Historia
**Como cliente**, quiero filtrar beneficios por *Todos / Recompensas / Promociones*; el filtro *Misiones* se habilita únicamente en fase **V1** cuando LL-30 y LL-31 estén listas. Cada tarjeta indica tipo, comercio, condición, vigencia, elegibilidad y flujo de canje mediante QR o código manual (LL-23). Los puntos son acumulativos permanentes y no existe débito ni gasto de puntos.

---

## Criterios de Aceptación y Reglas Verificables
1. **Filtros Clasificatorios sin Duplicados**:
   - Pestañas *"Todos"*, *"Recompensas"*, *"Promociones"*.
   - El filtro *"Misiones"* se mantiene oculto en fase **MVP** y solo se activa cuando la fase **V1** está explícitamente habilitada (`phase=v1` o variable de entorno de fase).
   - Clasificación limpia y sin duplicados entre categorías.
2. **Campos Requeridos en Cada Tarjeta**:
   - **Tipo**: Identificador explícito (*Recompensa*, *Promoción*, *Misión*).
   - **Comercio**: Nombre del negocio emisor y enlace a su ficha.
   - **Condición**: Regla de obtención (ej. *"Requiere 100 puntos acumulados (no se descuentan)"*, *"15% de descuento"*).
   - **Vigencia**: Fechas de inicio/término calculadas en servidor.
   - **Elegibilidad**: Estado de cumplimiento (`eligible: true/false`) evaluado en el servidor basado en puntos de fidelidad, sellos independientes y cupos restantes.
3. **Flujo de Validación QR / Código Manual (LL-23)**:
   - Los beneficios elegibles despliegan el componente `ClaimQr` para generar el token temporal de un solo uso con fallback de código manual accesible.
   - El canje atómico se completa exclusivamente tras la confirmación del comercio (LL-23); beneficios no elegibles, expirados o sin cupo no permiten presentar éxito falso.
4. **No Hay Canje de Puntos**:
   - Los puntos de fidelidad son marcadores de nivel permanente; ningún canje descuenta puntos locales ni los gasta.
5. **Manejo de Estados**:
   - Estados de carga (shimmers).
   - Estados vacíos contextuales para cada filtro.
   - Estado de error de red con botón de reintento.

## Implementación Técnica

### 1. Backend (Django REST Framework)
- `backend/loyalty/discovery_api.py`:
  - `DiscoveryView.get(slug=None)` enriquece las listas de `rewards` y `campaigns` con `business_name`, `business_slug`, `condition`, `eligible`, `starts_at`, `ends_at` y `remaining_quota`.
  - Exclusión automática de beneficios asociados a comercios inactivos.
  - `missions` controladas por fase: se retornan únicamente si se solicita `phase=v1`.

### 2. Frontend Web (Next.js)
- `app/c/recompensas/page.tsx`:
  - Componente interactivo cliente con pestañas *"Todos"*, *"Recompensas"*, *"Promociones"* (y *"Misiones"* al recibir `phase=v1`).
  - Tarjetas con tipo, comercio, condición, vigencia y badge de elegibilidad calculado por el servidor.
  - Integración del flujo de canje `ClaimQr` (QR + código manual) para beneficios elegibles.
  - Botón bloqueado con motivo para beneficios donde aún no se cumplen condiciones.
  - Tarjetas de resumen con puntos permanentes acumulados y sellos independientes.
- `lib/data/customer.ts`:
  - Tipos `CustomerBenefitItem`, `CustomerBenefitsResult` y función `getCustomerBenefits(phase)`.

### 3. Mobile App (Expo / React Native)
- `mobile/src/app/recompensas.tsx`:
  - Tabs dinámicas: `["Todos", "Recompensas", "Promociones"]` en MVP; `["Todos", "Recompensas", "Promociones", "Misiones"]` en V1.
  - Sección de misiones restringida a fase V1.
  - Navegación hacia `beneficio.tsx` con verificación de elegibilidad y modal de QR/código manual para LL-23.
